# Task

## Goal

사진 편집의 의도를 문장으로 쓰기 어려운 사용자가 **현재 사진에 맞는 짧은 추천 문장 최대 3개 중 하나를 선택 → 필요하면 수정 → 전송 → 편집 계획 확인 → 적용**할 수 있도록, 기존 ‘지시’ 도구에 선택형 넛지를 추가한다.

## Background

2026-10-07 사용자 요청: 자신의 의도를 쉽게 표현하기 어려우므로 해당 사진에 적합한 추천 프롬프트를 넛지 방식으로 제안한다.

### 확인한 현재 구조

- `EditorRoute.kt:DirectToolSheet`는 `VoicePromptBar`를 `direct.setRequest/submit`에 연결한다. 현재는 예시 placeholder와 자유 입력만 있고 사진 맞춤 추천은 없다.
- `DirectController`는 요청 문장·계획·실행 상태를 소유한다. `EditPlanProvider.plan(preview, request)`로 계획을 얻고 `PlanRunner.validate` 이후 보여준다. `적용` 전에는 편집하지 않으며 실행은 기존 단계별 history 계약을 따른다.
- `GeminiPlanProvider`는 현재 미리보기를 `GeminiImageCodec`으로 축소·인코딩하고 Gemini에 보낸다. 기존 설정·HTTP·오류·취소 경로를 재사용할 수 있다. 추천을 얻으려고 가짜 편집 요청으로 `plan()`을 호출해서는 안 된다.
- `PortraitDetector`는 원본의 얼굴 존재 여부만 반환하는 메뉴용 신호다. 풍경·음식·역광·사진 분위기를 판별하는 범용 분석기가 아니며, 크롭/보정 이후 현재 사진의 근거로 그대로 쓸 수 없다.
- `DirectHost.canvas()`는 document와 preview를 함께 읽지만 렌더 revision의 일치를 보장하지 않는다. `requestPreview()`는 실패 시 이전 preview를 유지한다. 추천에는 **분석한 프레임과 현재 문서가 같은 revision인지** 확인하는 최소 연결이 필요하다.
- `DirectController.setRequest()`는 현재 문장만 바꾼다. 추천 문장으로 교체하거나 직접 수정한 뒤 이전 계획을 적용할 수 없도록, 이번 입력 흐름 안에서 계획 무효화도 처리한다.

### 제품 판단 및 첫 범위

사용자가 처음부터 목적·대상·강도·스타일을 모두 설명하게 하지 않는다. 먼저 알아보기 쉬운 **결과 방향 3개 이하**를 보여주고, 한 번의 선택으로 완성된 문장을 얻도록 한다. ‘프롬프트’, ‘노출 +0.3’ 같은 용어보다 ‘조금 더 밝게’, ‘따뜻한 분위기로’처럼 결과를 말한다.

이번 범위는 **지시 시트 안의 사진 맞춤 문장 추천** 한 개의 기능 슬라이스다. 자유 생성된 무제한 문장 대신 앱에서 검토한 소규모 문장 카탈로그를 두고, 기존 Gemini 연결로 현재 사진에 적합한 ID를 선택·정렬한다. 사진별 추천은 실제 이미지 분석을 거쳐야 하며, 고정 예시나 얼굴 검출만으로 맞춤 분석을 했다고 표시하지 않는다.

이 방식은 표현 범위가 제한되는 대신 현재 편집기가 처리할 수 있는 제안, 한국어 품질, 실패 시 대체 경로를 검증하기 쉽다. 추천 클릭은 문장 입력만 수행한다. 자동 전송·즉시 편집은 하지 않는다. 추천 분석 1회와 사용자의 전송 후 계획 생성 1회는 별도이며, 추천마다 계획을 미리 생성하지 않는다.

- 무관한 미커밋 변경과 `work/REVIEW.md`. task/result/review 사본 생성 및 자동 commit/push.

## Requirements

### 1. 넛지 UI와 선택 동작

1. 지시 시트의 입력창 바로 아래에 보조 영역을 둔다. 첫 진입에는 `이렇게 말해보세요`와 일반 예시 3개(`조금 더 밝게`, `따뜻한 분위기로`, `색감을 자연스럽게`)를 즉시 표시한다. 이 예시에는 사진 분석 완료를 암시하는 제목/설명을 붙이지 않는다.
2. 같은 영역에 `사진에 맞는 문장 보기` 동작을 제공한다. `현재 사진의 축소본을 Gemini에 보내 추천해요`라는 짧은 안내를 함께 표시하고 **이 동작을 누른 때만** 맞춤 분석을 시작한다. 별도 확인 다이얼로그는 없다. 사진 열기·시트 진입·타이핑·재구성만으로 추가 이미지 전송을 하지 않는다. 기존 지시 도구의 키 미설정 시 설정 열기 동작은 유지한다.
3. 성공하면 제목을 `이 사진에는 이런 방향도 좋아요`로 바꾸고 최대 3개의 다른 방향을 표시한다. 순위를 강조하는 배지·기본 선택·‘필수 보정’·외모 결점 지적·확정적 품질 약속은 없다. 1~2개만 적합하면 그 수만 보여주며 3개를 억지로 채우지 않는다.
4. 추천 pill 하나를 누르면 해당 **완성 문장만 입력창에 채운다**. 그 순간 planning/provider/runner/commit 호출은 0회이고 사진·문서·history는 그대로다. 사용자는 타이핑 없이 전송할 수도, ‘조금’을 바꾸는 등 문장을 수정할 수도 있다. 입력만으로 키보드를 강제로 열지 않고 직접 입력창을 누르면 수정 가능해야 한다.
5. 빈 입력 또는 수정하지 않은 추천 초안일 때만 추천을 노출한다. 사용자가 직접 타이핑/수정하거나 음성 인식을 시작하면 추천 목록을 숨겨 초안을 덮어쓰지 못하게 한다. 전체 삭제 후 빈 입력으로 돌아오면 같은 revision의 목록을 다시 표시한다. 추천 초안 여부는 단순 문자열 비교가 아니라 입력 출처로 관리한다.
6. 추천을 고른 상태에서는 다른 추천으로 교체할 수 있다. 보조 문구 `문장을 바꿔도 좋아요`로 수정 가능성을 알려준다. 추천 완료 응답은 목록만 갱신할 수 있고 입력창을 자동으로 채우거나 바꾸지 않는다.
7. 추천 영역의 `숨기기`는 현재 지시 시트 세션 동안 유지한다. 타이핑 중이거나 숨긴 뒤 도착한 응답이 영역을 다시 펼치지 않는다. 새 시트 세션에서는 다시 표시할 수 있다. 자동 순환·깜빡임·반복 팝업은 없다.
8. 전송하면 기존 계획 생성과 한국어 단계 목록을 사용하고 사용자가 `적용`해야 편집한다. 요청 문장이 바뀌면 기존 대기 계획과 `canApply`를 즉시 무효화한다. 이전 문장에 대한 늦은 계획 응답도 새 문장에 붙이지 않는다. 적용 실행 중에는 추천 변경을 허용하지 않는다.

### 2. 사진을 근거로 한 제한된 추천

9. 카탈로그는 안정적인 ID, 짧은 한국어 label, 완성 request, 결과 방향 설명, 지원 capability를 갖는다. UI 문자열은 리소스에 두고 `core:ai`에는 ID/추천 계약과 분석용 설명만 둔다. 다음 8개를 초기 카탈로그로 사용한다. 표현을 다듬어도 의미와 실행 가능 경계는 유지한다.

| ID | label | 입력될 완성 문장 | 지원 방향 |
| --- | --- | --- | --- |
| brighten | 조금 더 밝게 | 사진 전체를 조금 더 밝게 해줘 | Exposure 증가 |
| lift_shadows | 어두운 부분을 밝게 | 사진 전체의 어두운 부분을 조금 밝게 해줘 | Shadows 증가 |
| soften_highlights | 밝은 부분을 부드럽게 | 사진 전체의 너무 밝은 부분을 조금 어둡게 해줘 | Highlights 감소 |
| warm | 따뜻한 분위기로 | 사진 전체의 색감을 조금 따뜻하게 해줘 | Temperature 증가 |
| cool | 시원한 분위기로 | 사진 전체의 색감을 조금 차갑게 해줘 | Temperature 감소 |
| natural_color | 색감을 자연스럽게 | 사진 전체의 과한 채도를 조금 낮춰줘 | Saturation 감소 |
| vivid_color | 색감을 생생하게 | 사진 전체의 채도를 조금 높여줘 | Saturation 증가 |
| film_warm | 따뜻한 필름 느낌으로 | 사진 전체에 따뜻한 필름 스타일을 약하게 적용해줘 | 기존 FilmWarm 스타일 |

10. 모델은 **현재 편집 결과의 preview**와 이 카탈로그를 보고 적합한 ID를 우선순위로 반환한다. 어두운 장면을 무조건 실패한 사진으로 판단하지 말고 현재 분위기를 유지할 수 있는 방향도 고려하도록 지시한다. `warm/cool`, `natural_color/vivid_color`처럼 상반된 후보는 함께 제시하지 않는다. `brighten/lift_shadows`, `warm/film_warm`처럼 유사한 방향도 한 목록에서는 대표 하나를 우선한다. 충돌 그룹은 앱에서도 검사한다.
11. 기계가 읽는 응답은 ID 목록뿐이다. 기존 function-calling 구조처럼 검증 가능한 응답을 사용하고, 모델의 자유 서술·새 ID·임의 수치·임의 편집 명령을 UI/실행에 전달하지 않는다. 순서를 보존하며 중복·미지원 ID·충돌 후보를 제거한 후 최대 3개를 사용한다. 정상적인 빈 추천은 오류와 구별한다. 잘못된 JSON/응답 구조, 차단/잘린 응답은 실패로 처리한다.
12. 설명이 필요하면 카탈로그의 조건형 문구(`어두운 부분을 더 보고 싶다면` 등)를 쓴다. 실제 관찰을 담은 자유 생성 근거를 꾸며서 붙이지 않는다. 카탈로그 전체를 공개하거나 장르 설문을 먼저 요구하지 않는다. 사진에 없는 인물/하늘/음식을 추천 문장에 끼워 넣지 않는다.
13. 추천은 입력 보조이므로 편집 계획을 반환하거나 미리 실행하지 않는다. 카탈로그의 capability는 지원 여부 검증용이며 실행 경로가 아니다. 선택한 문장은 **기존 EditPlanProvider**에 그대로 전달하고 계획 검증·단계 표시·실행 경계를 유지한다.

### 3. 상태·비용·실패·수명주기

14. 분석 대기/분석 중/맞춤 추천/빈 결과/실패/숨김을 구별한다. 분석 중에는 추천 영역 안에 `사진에 맞는 문장을 찾는 중`과 취소를 보여주고 자유 입력은 계속 가능하게 한다. 전송/음성 Final이 먼저 발생하면 추천 작업을 취소하고 사용자의 기존 계획 요청을 우선한다.
15. preview 준비 중에는 분석 시작을 비활성화하고 `사진을 준비하는 중`을 표시한다. 문서와 일치하는 렌더가 완료돼야 활성화한다. 이전 revision의 프레임이나 실패 후 남은 preview로 요청하지 않는다. 현재 preview에 UI overlay·선택 윤곽·가이드가 섞여서는 안 된다.
16. 한 번의 명시적 추천 동작은 네트워크 호출 최대 1회다. 연속 탭은 합치고 자동 재시도는 없다. 요청 전체 timeout은 12초로 두고 취소 가능한 구조로 구현한다. 완료된 동일 revision의 결과는 현재 편집 화면 생존 기간에 재사용하며 재구성·시트 재진입으로 재호출하지 않는다. 캐시는 최신 한 항목의 작은 결과만 메모리에 보유하고 이미지/문장 이력을 디스크에 저장하지 않는다.
17. 문서 변경(Undo/Redo/크롭/보정 포함), 프로젝트 변경, Gemini 설정 변경 시 이전 추천을 무효화하고 진행 중 분석을 취소한다. 자동 재분석하지 않으며 사용자가 다시 요청해야 한다. 요청은 프로젝트·문서 revision·렌더 revision·시트 세션/요청 세대로 식별한다. 같은 사진이어도 다른 편집 상태의 결과가 섞이지 않게 하고, 취소에 협조하지 않는 fake의 늦은 결과도 차단한다.
18. 시트 닫기/다른 도구 전환/화면 이탈 시 in-flight 추천을 취소한다. 정상 구성 변경은 ViewModel 상태를 유지하여 중복 호출하지 않는다. process death 이후에는 초안/추천 복구를 새로 도입하지 않고 기존 복구 정책에 따라 초기화한다. 추천 취소는 문장·사진·history를 바꾸지 않는다.
19. 네트워크/timeout/인증/잘못된 응답은 기존 오류 매핑으로 짧은 한국어 snackbar를 표시하고 일반 예시로 복귀한다. 적합한 후보 0개는 `다른 방향을 직접 말해보세요` 같은 보조 문구와 일반 예시를 사용한다. 둘 다 직접 입력·음성·전송을 막지 않는다. `다시 찾기`는 사용자 명시 동작이며 실패/취소 후 자동 루프가 없어야 한다.
20. 기존 `GeminiSettings`, HTTP 계층, `GeminiImageCodec`의 축소 JPEG 경로(긴 변 1024 이하)를 재사용한다. 키·이미지·사용자 초안을 로그에 남기지 않고 추천 요청에는 초안/EXIF/파일 경로를 추가하지 않는다. 인코딩/픽셀 처리/네트워크는 main thread 밖에서 수행한다. 공유 preview를 recycle하지 않고 임시 bitmap만 정리한다. 모델·의존성·새 서버를 추가하지 않는다.
21. 추천 상태와 job은 기존 지시 controller 경계에 소유시키고 UI는 값/이벤트만 전달한다. 큰 controller가 될 경우 같은 패키지의 작은 협력 객체로 나눌 수 있다. 별도 ViewModel/전역 추천 서비스/새 편집 실행기를 만들지 않는다.

### 4. 디자인·명세 정합성

22. 기존 pill, `editSurfaceRaised`, typography/간격 토큰을 사용한다. 최대 3개의 짧은 추천 pill을 가로 스크롤 한 줄에 두고, 48dp 터치 영역과 TalkBack label을 제공한다. 설명은 `누르면 문장이 입력돼요`처럼 결과가 명확해야 한다. 글자 확대/작은 화면/키보드 표시에서도 입력과 고정 취소·적용이 가려지지 않게 하고, 시트 45%/캔버스 절반 이상 규칙을 지킨다. 초점 강제 이동이나 화면 읽기 반복 알림은 없다. 적용만 주 accent를 갖는다.
23. 기존 명세와의 차이를 명시적으로 반영한다.
   - `specs/vibe_edit.md`의 ‘요청당 한 번의 계획 호출’은 유지한다. 추천은 별도의 명시적 읽기 전용 요청이며 계획 생성/실행 단계가 아니라는 설명을 추가한다.
   - `DESIGN.md` §4 상태 표시의 AI 작업 canvas overlay 기본 규칙에 **입력 보조용 읽기 전용 추천만 인라인 진행+취소를 사용**하는 제한된 예외를 기록한다. 기존 planning/running overlay 동작은 유지한다.
   - `specs/prompt_input.md`의 기존 음성 Final 자동 전송은 유지한다. 추천 선택만 자동 전송하지 않으며, 선택/채우기 도구의 기존 의미는 바꾸지 않는다.
   - `specs/vibe_edit.md`의 단계 목록은 계속 검증된 PlanStep 템플릿에서 나온다. 추천 label/request도 앱 카탈로그에서 나오므로 모델 자유 서술을 단계 목록으로 렌더링하지 않는 계약을 유지한다.

## Acceptance Criteria

- [ ] 지시 시트에서 일반 예시가 즉시 보이고, 맞춤 요청 전에는 추가 네트워크 호출이 0회다.
- [ ] 현재 preview를 실제 분석해 서로 다른 방향의 문장 최대 3개를 추천한다. 고정 목록을 사진 맞춤으로 표시하지 않는다.
- [ ] 추천 한 번 선택으로 완성 문장이 입력되고, 수정/전송/계획 확인/적용으로 이어진다. 선택만으로 계획 생성·편집·history 변경은 없다.
- [ ] 직접 입력/음성/숨김을 추천 응답이 방해하지 않는다. 문장 변경 후 이전 계획은 적용할 수 없다.
- [ ] 분석 실패·빈 결과·취소에도 일반 예시와 자유 입력을 사용할 수 있고, 재구성·재진입·연속 탭이 중복 요청을 만들지 않는다.
- [ ] 렌더 대기/실패, 문서·설정 변경, 시트 닫기, 늦은 응답에서 잘못된 사진의 추천/계획을 채택하지 않는다.
- [ ] 지원하지 않는 기능/자유 생성 명령/상반되거나 중복된 추천은 표시하지 않는다.
- [ ] 작은 화면·큰 글자·키보드·TalkBack 및 진행/빈/실패/성공 상태를 확인한다.
- [ ] 관련 테스트와 canonical 검사가 통과하고 실제 사진 적합성 확인 결과 또는 미실행 제한을 RESULT에 남긴다.
- [ ] 관련 명세/결정을 정합하게 갱신하고 무관한 변경과 이전 미해결 인계를 보존한다.

## Validation

개발 중 좁은 검사(새 테스트 이름에는 `Suggestion`을 포함해 필터에서 누락되지 않게 한다):

```bash
./gradlew --offline --quiet :core:ai:testDebugUnitTest --tests '*Suggestion*' --tests '*GeminiPlan*'
./gradlew --offline --quiet :feature:editor:testDebugUnitTest --tests '*Suggestion*' --tests '*Direct*' --tests '*VoicePrompt*'
```

완료 검사:

```bash
scripts/check.sh
git diff --check
```

검증해야 할 행동:

- **client/provider**: MockWebServer로 올바른 현재 이미지/카탈로그, 이미지 축소, 키가 URL에 없음, ID 검증/충돌 제거/중복/초과/빈 결과, 잘못된 JSON/차단/401/429/5xx/timeout, 취소 시 call 종료. 실제 외부 API에 의존하는 단위 테스트는 금지한다.
- **controller/VM**: 시작 전 0회·명시적 요청 1회·캐시 재사용, 요청 중 직접 입력 유지, 추천 선택 시 planner/runner/commit 0회, 전송 후 planner 1회, 문장 변경 후 이전 plan 무효화, 닫기/설정 변경/Undo/Redo/다른 revision·늦은 결과 차단. 렌더 A가 남아 있는 문서 B 및 렌더 실패를 별도로 재현한다.
- **UI**: 최초/분석 중/성공/빈/실패/숨김/직접 입력/추천 초안 상태와 label→실제 request 매핑. 음성 시작 시 목록 숨김과 Final의 기존 전송 유지. 상태별 필요한 골든만 추가·갱신하고 육안 확인한다.
- **실사진 smoke**: 전송 권한 있는 사진 최소 6장(어두운 실내, 밝은 야외, 음식, 인물, 강한 색감, 의도적으로 어두운 야경 등)에서 맞춤 요청→추천 선택→필요시 수정→전송→계획→적용/Undo를 확인한다. 서로 다른 사진이 서로 다른 적합한 방향을 얻는지, 실패하면 일반 예시와 구별되는지 기록한다. 모든 사진에 다른 ID가 나와야 한다고 강제하지 않는다.
- 카탈로그 8개 문장의 계획 결과가 지원 방향과 맞는지 확인하고, 예상하지 않은 선택/삭제/생성 단계가 나오는 문장은 표현을 수정한 뒤 다시 확인한다. fake의 정답 반환만으로 실제 문장 해석 품질이 검증됐다고 쓰지 않는다.
- RESULT에는 입력 유형, 추천 ID/순서, 전송까지 사용자가 한 동작, 추천 지연/요청 수, 계획과 문장의 일치, 환경 제한을 간단한 표로 기록한다. 사용성 개선은 가설이며 실제 사용자 검증 없이 개선율이나 만족도를 주장하지 않는다. 별도 평가 시스템/원격 telemetry는 만들지 않는다.
- 실제 API 키/권한 있는 사진/기기가 없으면 해당 검증은 미실행으로 명시한다. 기존 로컬 ADB 전달 `127.0.0.1:15039` 연결 여부도 확인하되 키나 개인 사진을 결과에 노출하지 않는다.
